# CAN1 通信代码审查与局部精简

本次基于工作区已有修改继续处理，未烧录、复位或发送运动命令。不能据此认定两次实机通信故障的根因已消除。

## 通信路径

- 上位机 `llm-pid-tuner-main/hw/bridge.py` 负责串口握手、命令和接收；不直接驱动 CAN。
- `tuner.py` 记录 `# CAN` 诊断，只有 TARGET/TIMEOUT 且样本数足够才进入正常轮次分析；CAN FAULT、MOTOR FEEDBACK LOST 会终止本次调参。
- `robot_app.c` 执行安全检查和反馈轮询，`zdtEmm.c` 编解码，`zdtCan.c` 管理发送槽、邮箱及接收分发。
- 停车槽优先于普通命令，普通命令优先于速度槽；每轮最多提交三个邮箱，同一电机未发送的速度可被最新值覆盖。

## 本次修复

1. 原停滞检测在 EWGF/EPVF 时把观察时间从 150 ms 缩短为 50 ms，仍可能 Stop/Start。发送报错并不能证明邮箱卡死。现在 EWGF/EPVF/BOFF 都退出强制重启观察，继续由现有安全门禁、邮箱超时和硬件恢复处理。
2. 原停滞观察一旦启动，即使后来邮箱已空闲，也可能累计 STALL_REC、丢弃软件队列。现在观察到期时必须仍然 FREE=0 才执行强制恢复，避免将已结束的发送当作停滞。
3. 强制恢复原先清空未发送的停车槽。现在只丢弃普通命令和速度，保留软件停车请求。已提交后被撤销的停车帧仍依赖现有停车确认与重试机制。
4. Stop/Start/通知恢复原先忽略返回值，随后无条件 ResetError。现在检查每一步，失败时保留错误，不累计成功恢复；Start 本身会清 HAL 错误，因此先保存诊断且删除多余 ResetError。
5. 接收地址原先截为 8 位，`0x10100` 可以误认成 motor 1 的 `0x100`。现在验证完整地址，避免其他扩展 ID 刷新四轮反馈新鲜度。
6. BeginStop 复用普通队列清理函数，消除重复实现；校正 RX 计数、硬件过滤器和就绪条件注释。

保留命令格式、统计字段、EMM/X 协议、停车重试、速度覆盖和使能延迟；未修改 PID、300 ms 新鲜度门槛、CAN1 位时序、CAN2/G6220。上位机本次只审查和运行测试，没有修改业务逻辑。

## 尚需注意的设计问题

- `ChassisSafety_Process` 每轮 ConsumeFault 会清锁存，而传输层还有 100 ms 自动解锁、500 ms 空闲恢复及运动开始前 ClearFault，职责重叠。软件超时事件若间隔出现，100 ms 连续故障计时可能被中间无事件的循环重置。实时 ESR 不健康仍直接拒绝运动，反馈超时仍停车。本次保留该门禁策略；后续应把“事件读取”和“故障确认解除”分开，并以应用层时序测试统一管理，不能仅删除恢复分支。
- FREE=0、TX_OK 不增长只是停滞迹象，不是硬件损坏证明。HAL Abort 是异步请求；当前 Stop/Start 保底路径也使用 HAL 内部等待，不是严格全程非阻塞。纯软件测试不能证明实际外设恢复行为。
- 使能延迟在提交使能帧时开始计时，并可阻塞队头之后的其他电机帧。它不等于电机已完成使能确认。本次保留既有时序，避免未经实机验证改变驱动器启动流程。
- RX 是 HAL 收到的全部帧数，TX_OK 只证明 CAN 帧完成，均不等于四轮速度反馈有效。还必须比较 MOTOR FEEDBACK 各轮 SEQ/AGE。

## 验证结果

- `python tools/run_c_tests.py`：5 组通过，其中 control layer 14 个测试组。
- 新增覆盖错误状态禁止强制恢复、空闲邮箱不产生伪恢复、停车槽保留、Stop 失败保留错误、扩展 ID 不别名。
- 上位机 unittest discover：`test_hw_bridge.py` 9 项、`test_hardware_tui.py` 10 项通过。
- `tools/build_firmware.py` 配合本机 STM32 GCC：46 个编译单元及链接通过，生成 `tmp/firmware/serialPlotTest.elf`。

实机复测仍需在复位前保存至少两次 CAN STATUS / MOTOR FEEDBACK，比较 TEC、REC、TX_OK、RX、FREE、TX_TIMEOUT、STALL_REC 和每轮反馈序号。先验证停车及低速通信，再验证原有负载条件；本次测试结果不构成可用的 X PID 调参结果。
